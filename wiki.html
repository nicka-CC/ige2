1. Главное отличие: Ссылка против Значения

Все типы данных в C# делятся на две фундаментальные категории. Это база, определяющая поведение переменных при присвоении и передаче.

struct

value type

Значимый тип. При присвоении копируется само ЗНАЧЕНИЕ (данные). Каждая переменная имеет собственную независимую копию.

C# Struct struct Point { public int X; } // Выполнение: Point p1; p1.X = 10; Point p2 = p1; // КОПИРОВАНИЕ данных p2.X = 20; // Результат: p1.X == 10; // p1 не изменился!

class

reference type

Ссылочный тип. При присвоении копируется ССЫЛКА на объект, а не сам объект. Обе переменные указывают на один участок памяти.

C# Class class Point { public int X; } // Выполнение: Point p1 = new Point(); p1.X = 10; Point p2 = p1; // Копируется ССЫЛКА p2.X = 20; // Результат: p1.X == 20; // Обе указывают на одно и то же!
САМАЯ ВАЖНАЯ ЛОВУШКА ГОСА

На экзамене 99% будет практический кодовый вопрос вроде этого. Студенты машинально думают, что в обоих случаях изменения одного повлекут изменения другого, забывая, что структура при присвоении создает полную физическую копию.

2. Передача параметров в методы

Вот здесь кроется половина всех каверзных вопросов. Запомните: передача в метод работает точно так же, как обычное присваивание.

Передача struct

При передаче структуры в метод создается ее копия в стеке метода. Все изменения внутри метода происходят с локальной копией и исчезают при выходе.

C# Code void Change(Point p) { p.X = 100; } // Вызов: Point p1; p1.X = 10; Change(p1); // На выходе: p1.X == 10; // Исходная структура НЕ изменилась!

Передача class

Передается копия ссылки. Обе ссылки (внутри метода и снаружи) указывают на один и тот же объект в куче. Изменения объекта внутри метода видны снаружи!

C# Code void Change(Point p) { p.X = 100; } // Вызов: Point p1 = new Point(); p1.X = 10; Change(p1); // На выходе: p1.X == 100; // Объект в куче ИЗМЕНИЛСЯ!
ОЧЕНЬ ВАЖНАЯ ФОРМУЛИРОВКА ДЛЯ ОТВЕТА БИЛЕТА

«Для ссылочных типов при вызове метода копируется НЕ сам объект в памяти, а ССЫЛКА на данный объект. Поэтому метод работает с тем же физическим экземпляром объекта в куче».

3. Память (Где они живут?)

На госе глубокого анализа рантайма CLR не просят. Но знание базового распределения — строго обязательно.

СТЕК (Stack)

Быстрый, фиксированный

Сюда попадают локальные переменные, адреса вызовов и сами значения структур (struct). Очищается автоматически при выходе из метода.

Point p_struct { X: 10 }
Point p_class_ref Адрес: 0x7FF8

КУЧА (Heap)

Большая, управляется GC

Сюда попадают все ссылочные объекты (class). Переменная в стеке лишь хранит адрес на этот блок в куче. Очищается сборщиком мусора (Garbage Collector).

Адрес: 0x7FF8 Объект { X: 20 }
Другие объекты... данные...
Кликните по ячейкам стека, чтобы увидеть связи в памяти!
УПРОЩЕНИЕ ДЛЯ ЭКЗАМЕНА

На госе говорите просто: «Классы размещаются в куче (heap), а структуры — в стеке (stack)». Это небольшое упрощение (так как поля структуры внутри класса будут лежать с ним в куче), но на экзаменах от вас ждут именно этой классической формулировки.

4. Наследование — главный запрет структур

Этот теоретический вопрос очень часто задают дополнительно, чтобы проверить понимание ООП.

Структуры

НЕТ

❌ Структура НЕ может наследоваться от классов или других структур.
❌ Структура НЕ может служить базой для других классов/структур (все структуры неявно помечены как sealed).

Классы

ДА

✅ Поддерживают одиночное наследование классов.
✅ Могут быть базовыми для других классов и наследоваться от абстрактных классов.

«ПРЕПОД СКАЗАЛ» (Важная фишка для 5-ки)

Несмотря на отсутствие наследования, все структуры неявно наследуются от System.ValueType, который в свою очередь наследуется от System.Object. Это обеспечивает наличие у структур базовых методов ToString(), Equals() и др. Также структуры могут реализовывать интерфейсы!

Внимание

«В билетах и ответах мы считаем по СТАРЫМ правилам!»

• Класс — может иметь явный пользовательский конструктор без параметров.

10 Экспресс-примеров на Class vs Struct

Смысл тренажера — не просто смотреть готовые ответы. Перед тем как нажать на кнопку, самостоятельно прочитайте код и попытайтесь дать ответ на вопрос: «Что выведет этот код или есть ли здесь ошибка?». Только после этого сверяйтесь с объяснением.

Пример 1: Struct — копия данных
C# Code struct Point { public int X; } Point p1; p1.X = 10; Point p2 = p1; p2.X = 50; Console.WriteLine(p1.X);
Выведет: 10

Почему: Так как Point объявлен как struct (значимый тип, value type), строка Point p2 = p1 копирует структуру целиком, создавая независимый дубликат в стеке. Изменение p2.X не оказывает абсолютно никакого влияния на исходную переменную p1.
Пример 2: Class — ссылка на один объект
C# Code class Point { public int X; } Point p1 = new Point(); p1.X = 10; Point p2 = p1; p2.X = 50; Console.WriteLine(p1.X);
Выведет: 50

Почему: Поскольку Point является классом (ссылочный тип, reference type), при присваивании Point p2 = p1 копируется лишь ссылка на объект в управляемой куче. Обе переменные указывают на один физический экземпляр. Модификация p2.X = 50 меняет поле общего объекта, поэтому p1.X тоже вернет 50.
Пример 3: Struct в методе (передача значения)
C# Code struct Point { public int X; } void Change(Point p) { p.X = 100; } Point p1; p1.X = 5; Change(p1); Console.WriteLine(p1.X);
Выведет: 5

Почему: По умолчанию структуры передаются в методы по значению. В метод Change уходит локальная копия структуры p1. Метод меняет значение поля у этой копии в собственном стеке вызовов. После завершения работы метода локальная копия уничтожается, а оригинальная структура p1 остается нетронутой.
Пример 4: Class в методе (передача ссылки)
C# Code class Point { public int X; } void Change(Point p) { p.X = 100; } Point p1 = new Point(); p1.X = 5; Change(p1); Console.WriteLine(p1.X);
Выведет: 100

Почему: В метод передается копия ссылки на объект. Таким образом, аргумент p внутри метода указывает на тот же самый объект в куче, что и внешняя переменная p1. Изменение поля p.X = 100 успешно изменяет реальный объект.
Пример 5: Повторное присваивание ссылки
C# Code class A { public int X; } A a1 = new A(); a1.X = 1; A a2 = a1; a2 = new A(); a2.X = 99; Console.WriteLine(a1.X);
Выведет: 1

Почему: Изначально a1 и a2 ссылаются на один объект (у которого X = 1). Затем инструкция a2 = new A() заставляет переменную a2 переключиться на **совершенно новый объект** в куче. У этого нового объекта поле X устанавливается в 99. При этом a1 по-прежнему продолжает безраздельно ссылаться на старый объект со значением 1.
Пример 6: struct внутри struct
C# Code struct Point { public int X; } Point p1; p1.X = 7; Point p2 = p1; p2.X++; Console.WriteLine(p1.X);
Выведет: 7

Почему: Переменная p2 получает копию данных. Инкремент p2.X++ увеличивает координату X у p2 до 8, но оригинальная структура p1.X остается равна первоначальному значению 7.
Пример 7: Null и class
C# Code class Test { } Test t = null;
Ответ: Ошибки нет. Это валидный код.

Почему: Классы (class) представляют собой ссылочные типы (reference types), а значит, переменная этого типа может хранить пустое значение null (указывать на «ничто»). Значимые типы (например, структуры struct) не поддерживают присвоение null напрямую.
Пример 8: Наследование struct
C# Code struct A { } struct B : A { }
Ответ: Ошибка компиляции!

Почему: В C# структуры не поддерживают наследование пользовательских типов. Структура не может наследоваться от другой структуры или класса (она неявно запечатана — sealed).
Пример 9: Передача ссылки
C# Code class Box { public int Value; } void Set(Box b) { b.Value = 500; } Box box = new Box(); box.Value = 1; Set(box); Console.WriteLine(box.Value);
Выведет: 500

Почему: Box является ссылочным типом, поэтому при вызове метода копируется лишь ссылка на объект. Метод Set получает доступ к оригинальному объекту в куче и перезаписывает значение его поля на 500.
Пример 10: struct vs class — главная ловушка
C# Code // Дано: Point p1 = new Point(1, 1); Point p2 = p1; p2.X = 20; // Вопрос: в каком случае изменится p1.X?
Ответ: Только если Point объявлен как class.

Почему:
• Если Point — это **class** (ссылочный тип), то p2 скопирует ссылку, и изменение p2.X = 20 приведет к изменению p1.X до 20.
• Если Point — это **struct** (значимый тип), то p2 скопирует данные, изменение p2.X = 20 произойдет в изолированной копии в стеке, и p1.X останется равным 1.

Вопрос 1: Что выведет данный кодовый фрагмент?
struct Point { public int X; } // ... Point p1; p1.X = 10; Point p2 = p1; p2.X = 25; Console.WriteLine(p1.X);
Верно! Так как Point — это структура (struct), при выполнении Point p2 = p1 происходит побитовое копирование структуры в новую переменную. Изменение p2.X = 25 никак не затрагивает p1.X.
Вопрос 2: Какое из утверждений о наследовании структур в C# является ВЕРНЫМ?
Верно! В языке C# структуры полностью исключены из иерархии наследования пользовательских типов. Структура не может иметь базовый класс и не может быть унаследована. Однако она неявно является наследником System.ValueType.
Вопрос 3: Что произойдет при передаче структуры в обычный метод в качестве аргумента?
Правильно! По умолчанию все структуры передаются в методы по значению. Это означает создание полной независимой копии в стеке метода. Чтобы передать по ссылке, нужно использовать ключевые слова ref, in или out.

1. Inheritance (Наследование)

Процесс, при котором один класс (наследник) получает все свойства, методы, поля и события другого класса (базового). Это устраняет дублирование кода.

Наследование классов в действии

C# syntax

Синтаксически наследование обозначается двоеточием :. Дочерний класс получает доступ ко всем public и protected членам родителя.

C# Code class Animal { public void Eat() { Console.WriteLine("Eating..."); } } class Dog : Animal // Dog наследует Animal { // Наследует метод Eat() автоматически! }
ТИПИЧНЫЕ ВОПРОСЫ НА ТЕСТАХ

• Что означает двоеточие в коде классов? — Наследование.
• Какие типы поддерживают наследование? — Исключительно class. Структуры (struct) в наследовании пользовательских типов не участвуют.

2. Virtual (Виртуальные методы)

Модификатор virtual разрешает переопределять метод в дочерних классах. У виртуального метода обязательно должна быть стандартная реализация по умолчанию.

C# Code class Animal { public virtual void Sound() { Console.WriteLine("..."); // Стандартный код } }
🚀 Главная суть: Объявление метода как virtual говорит компилятору: «Этот метод имеет базовый код, но дочерний класс имеет право изменить это поведение с помощью полиморфизма».

3. Override (Переопределение)

Модификатор override используется в дочернем классе для изменения логики работы родительского virtual или abstract метода.

C# Code class Dog : Animal { public override void Sound() // Переопределяем метод { Console.WriteLine("Woof"); } }
⚠️ Священное правило ГИА: Ключевое слово override может работать только в связке с virtual (в обычном классе) или abstract (в абстрактном классе). Попытка применить override к обычному не-виртуальному методу родителя вызовет ошибку компиляции!
ТИПИЧНАЯ ЛОВУШКА НА ГИА

В билете дадут класс A с обычным методом void Test() и класс B : A с методом override void Test(). Это ошибка компиляции! Без ключевого слова virtual в классе A переопределение невозможно.

4. Abstract (Абстракция — Любимец экзаменаторов)

Абстрактные элементы служат заготовками, шаблонами структуры и поведения, заставляя программиста прописывать детальную реализацию в наследниках.

abstract class

Класс-шаблон. Его экземпляр НЕЛЬЗЯ создать напрямую через new. Нужен для задания общей архитектуры.

C# Code abstract class Animal { } // В коде: Animal a = new Animal(); // ОШИБКА!

abstract method

Метод без какой-либо реализации (без фигурных скобок). Наследник абстрактного класса обязан реализовать его через override.

C# Code abstract class Animal { public abstract void Sound(); // Нет {} }
Разница между virtual и abstract:
Свойство Виртуальный (virtual) Абстрактный (abstract)
Наличие тела метода (кода) Есть тело метода { ... } Тела нет. Завершается точкой с запятой
Обязательность override Необязательно (используется базовый код) Обязательно реализовать в дочернем классе
Создание экземпляра Разрешено (в обычном классе) Категорически запрещено без наследника

5. Interface (Интерфейс — Контракт поведения)

Интерфейс — это чистый архитектурный контракт. Он только декларирует, какие методы, свойства и события должен иметь класс, реализующий данный интерфейс.

C# Code interface IMove { void Move(); // Сигнатура метода без модификаторов доступа } class Car : IMove { public void Move() // Обязаны реализовать в public виде! { Console.WriteLine("Driving..."); } }
📌 Главные отличия интерфейса от класса на ГИА:
• Интерфейс не имеет состояния (не может хранить нестатические поля данных).
• Содержит только сигнатуры методов (в классическом понимании C#).
• Объект интерфейса создать напрямую нельзя (new IMove() вызовет ошибку).

Override (Переопределение) Ключевое слово, с помощью которого дочерний класс меняет поведение virtual или abstract методов.
Abstract (Абстрактный) Шаблон. Экземпляр абстрактного класса создать **нельзя**. Абстрактный метод не имеет кода.
Interface (Интерфейс) Жесткий контракт поведения. Содержит только сигнатуры, не имеет полей. Нельзя вызвать через new.

Пример 1: Простое наследование
C# Code class Animal { public void Eat() { Console.WriteLine("Eat"); } } class Dog : Animal { } Dog d = new Dog(); d.Eat();
Выведет: Eat

Почему: Благодаря двоеточию class Dog : Animal, класс Dog наследует все public методы класса Animal. Метод Eat() становится доступен на объекте Dog напрямую.
Пример 2: virtual + override
C# Code class Animal { public virtual void Sound() { Console.WriteLine("Animal"); } } class Dog : Animal { public override void Sound() { Console.WriteLine("Dog"); } } Animal a = new Dog(); a.Sound();
Выведет: Dog

Почему: Рантайм CLR анализирует реальный тип созданного объекта (Dog), несмотря на то, что ссылка имеет тип Animal. Так как в базовом типе метод виртуальный, а в дочернем — переопределенный, вызывается полиморфный метод наследника.
Пример 3: override без virtual
C# Code class A { public void Test() { } } class B : A { public override void Test() { } }

Почему: Метод родителя A.Test() не помечен модификатором virtual или abstract. Переопределение невозможно.

Ответ: Ошибка компиляции!

Почему: Создание объектов абстрактных классов напрямую через new строго запрещено в C#.

Ответ: Реализации метода НЕТ (код валиден).

Почему: В C# абстрактные методы описываются исключительно сигнатурой (без фигурных скобок) и завершаются точкой с запятой. Любой дочерний не-абстрактный класс будет обязан переопределить этот метод.

C# Code abstract class Animal { public abstract void Sound(); } class Dog : Animal { public override void Sound() { Console.WriteLine("Woof"); } }

C# Code interface ITest { } // ... ITest t = new ITest();
Ответ: Ошибка компиляции!

Почему: Интерфейсы являются чистой декларацией поведения и не содержат реализации. Создать экземпляр интерфейса через new невозможно.
Пример 9: Полиморфизм
C# Code class A { public virtual void Show() { Console.WriteLine("A"); } } class B : A { public override void Show() { Console.WriteLine("B"); } } A obj = new B(); obj.Show();
Выведет: B

Почему: Объект в памяти имеет физический тип B. Так как в базовом типе A метод помечен как virtual, а в наследнике переопределен через override, то благодаря динамическому полиморфизму C# вызовет метод дочернего класса (B).

Почему: Значимые типы (структуры, struct) в C# запечатаны (неявно помечены как sealed) и категорически не могут использоваться в качестве базовых типов для наследования.

C# Code void Test(out int x) { Console.WriteLine(x); }

Почему: Внутри метода с параметром out категорически запрещено читать значение этого параметра до его первой явной инициализации (присвоения значения). Компилятор C# выдаст ошибку `Use of unassigned out parameter 'x'`.

Почему: Метод, принимающий параметр с модификатором out, обязан присвоить ему значение на всех путях выполнения до выхода из метода. Оставить его пустым нельзя.

C# Code void Test(out int x) { x = 42; } int a = 5; Test(out a); Console.WriteLine(a);

Почему: Передавать уже инициализированную переменную в качестве out параметра абсолютно разрешено. При этом её старое значение (5) полностью отбрасывается, и метод перезаписывает ячейку новым значением.

C# Code void Change(out int x) { x = 5; } int a = 10; Change(out a); Console.WriteLine(a);
Ответ: 5

Почему: Модификатор out перезаписывает внешнюю переменную. Исходное значение 10 заменяется внутри метода Change на значение 5.

C# Code void Test(ref int x) { x = x + 1; } int a; Test(ref a);

Почему: Модификатор ref жестко требует, чтобы переменная была инициализирована до её передачи в метод. Передавать неинициализированную a нельзя, так как метод имеет право сразу прочитать её текущее значение.

Ответ: Alice

Почему: Без ключевого слова ref, ссылка на объект p1 копируется по значению, и переназначение p = new Person(...) внутри метода изменило бы только локальную ссылку, оставив внешнюю p1 указывать на "Bob". Но благодаря ref, мы передали ссылку на саму ссылку, что позволило перенаправить оригинальную переменную p1 на новый объект в куче!
Пример 10: Передача структур по значению vs по ссылке
C# Code struct Point { public int X; } void Move(Point p) { p.X = 100; } void MoveRef(ref Point p) { p.X = 200; } Point pt = new Point { X = 10 }; Move(pt); Console.Write(pt.X + " "); MoveRef(ref pt); Console.Write(pt.X);
Ответ: 10 200

Почему: 1) Структура Point является значимым типом (Value Type). При обычном вызове Move(pt) в метод передается её полная копия, поэтому исходная структура снаружи осталась неизменной (10).
2) При вызове MoveRef(ref pt) мы передали структуру по ссылке, предоставив методу прямой доступ к оригинальной переменной, что позволило успешно изменить поле X на 200.

Мини-тест: Проверь себя на ref & out

Быстрый интерактивный опрос для закрепления правил инициализации параметров.

Вопрос 1: Какое из утверждений верно для ref параметров?
Абсолютно верно! Модификатор ref требует обязательной инициализации переменной до вызова. Метод может просто прочитать или изменить её, но не обязан это делать.
Вопрос 2: Что будет при компиляции метода: void Test(out int x) { x++; }?
Верно! Оператор x++ эквивалентен x = x + 1. В нем происходит чтение x. Но так как параметр помечен как out, читать его значение до явного присвоения запрещено, даже если переданная переменная была проинициализирована снаружи.
Вопрос 3: Какой модификатор параметра ОБЯЗЫВАЕТ метод гарантированно записать туда значение до возврата?
Да! Модификатор out накладывает строгое обязательство на вызываемый метод: до возврата управления (через return или конец метода) переменная должна быть записана.

1. База: Назначение блоков обработки исключений

Обработка исключений (Exception Handling) позволяет создавать отказоустойчивые приложения. При возникновении ошибки C# прерывает нормальный ход выполнения программы и ищет блоки обработки.

try

Опасный код

Блок кода, в котором потенциально может возникнуть ошибка (например, деление на ноль, обращение к null, чтение отсутствующего файла). Сам по себе без блоков catch или finally не компилируется!

try { int x = 10 / 0; // Деление на ноль! }

catch

Обработчик

Ловит возникшее в try исключение конкретного или общего типа. Предотвращает падение программы. Блоков catch может быть несколько (от частных исключений к общему Exception).

catch (DivideByZeroException e) { Console.WriteLine("На ноль делить нельзя!"); }

throw

Генератор

Принудительно вызывает ошибку (генерирует исключение). Мгновенно прерывает дальнейшее выполнение кода в текущем блоке и передает управление вверх по стеку вызовов.

if (user == null) { throw new ArgumentNullException(); }

finally

Гарант

Блок кода, который выполняется ВСЕГДА при выходе из try/catch (при успешном завершении, при возникновении ошибки или даже при срабатывании оператора return). Идеален для освобождения внешних ресурсов.

finally { file.Close(); // Закроется всегда! }

Перед тем как раскрыть ответ, внимательно вчитайтесь в код и проследите логику выполнения try/catch/finally блоков.

Пример 1: finally всегда выполняется?
C# Code try { Console.WriteLine("A"); } finally { Console.WriteLine("B"); }
Ответ: А и затем B

Почему: Блок try успешно выполнился, ошибок не было. Сразу после этого управление перешло в блок finally, который вывел B.
Пример 2: catch перехватывает исключение
C# Code try { int x = 10 / 0; } catch { Console.WriteLine("Error"); }
Ответ: Error

Почему: Деление на ноль выбрасывает DivideByZeroException. Блок catch перехватывает это исключение, не давая программе упасть, и выполняет обработку.
Пример 3: throw прерывает выполнение
C# Code Console.WriteLine("Start"); throw new Exception(); Console.WriteLine("End"); // Ошибка! Unreachable code
Ответ: Выведет Start, затем будет Ошибка компиляции!

Почему: Оператор throw безусловно прерывает ход программы. Компилятор видит, что строчка Console.WriteLine("End"); физически не может быть выполнена ни при каких условиях, и выдает ошибку: `CS0162: Unreachable code detected`.
Пример 4: try + catch + finally
C# Code try { throw new Exception(); } catch { Console.WriteLine("C"); } finally { Console.WriteLine("F"); }
Ответ: C и затем F

Почему: В try выбрасывается исключение, выполнение `try` прерывается. Блок catch перехватывает его и выводит C. После окончания блока catch обязательно выполняется блок finally, выводя F.
Пример 5: finally с return
C# Code try { return; } finally { Console.WriteLine("F"); }
Ответ: F (и затем выход из метода)

Почему: Это главная классическая ловушка! При срабатывании return внутри try, управление сначала ПРИОСТАНАВЛИВАЕТСЯ, выполняется обязательный блок finally (выведет F), и только после этого происходит фактический выход из метода.
Пример 6: Нет catch, но есть finally
C# Code try { throw new Exception(); } finally { Console.WriteLine("F"); }
Ответ: Выведет F, а затем программа аварийно падает!

Почему: Синтаксис без catch допустим. Возникает исключение, которое временно «замораживается», управление передается в обязательный блок finally (выведет F). После выхода из finally исключение возобновляет свое разрушительное действие и приложение завершается аварийно, так как никто не перехватил ошибку.
Пример 7: catch конкретного типа
C# Code try { throw new Exception(); } catch (Exception e) { Console.WriteLine("Handled"); }
Ответ: Handled

Почему: Класс Exception является базовым для всех типов исключений в .NET Framework. Блок catch (Exception e) успешно ловит абсолютно любую ошибку.
Пример 8: Код после throw внутри try (Ловушка!)
C# Code try { throw new Exception(); Console.WriteLine("A"); // Unreachable code } catch { Console.WriteLine("B"); }
Ответ: Ошибка компиляции!

Почему: Это еще одна каверзная ловушка на недостижимый код (Unreachable Code). Строчка Console.WriteLine("A"); следует безусловно сразу за throw, что приводит к ошибке сборки проекта.
Пример 9: Несколько catch (ловушка на порядок)
C# Code try { throw new Exception(); } catch (NullReferenceException) { Console.WriteLine("N"); } catch (Exception) { Console.WriteLine("E"); }
Ответ: E (Код полностью корректен)

Почему: Возникает общее исключение Exception. C# проверяет блоки сверху вниз: NullReferenceException не подходит, поэтому управление переходит ко второму блоку, который ловит базовый класс исключений и выводит E. Порядок правильный (сначала частное, затем общее).
Пример 10: finally + return + вывод возвращаемого значения
C# Code int Test() { try { return 1; } finally { Console.WriteLine("F"); } } Console.WriteLine(Test());
Ответ: сначала F, затем на следующей строке 1

Почему: При вызове Test() внутри try регистрируется return 1;. Однако немедленный выход блокируется. Выполняется блок finally, выводя в консоль F. Метод `Test` возвращает `1`, и внешний вызов Console.WriteLine выводит эту `1` на следующей строке!

Вопрос 1: Выполнится ли блок finally, если в блоке try сработал оператор return?
Абсолютно верно! Блок finally имеет наивысший приоритет. При вызове return в try/catch управление временно зависает, выполняется код в finally, и только потом происходит выход из метода.

1. База: public и private (Крайние степени доступа)

Эти два модификатора представляют собой противоположности в концепции скрытия данных: полная открытость против абсолютной изоляции.

public

Доступ везде

Члены класса с модификатором public видны абсолютно из любого места программы — внутри класса, в наследниках, из внешних классов и даже из других проектов (сборок).

class A { public int x = 10; } // Использование снаружи: A a = new A(); Console.WriteLine(a.x); // Работает!

private

Только внутри

Модификатор private ограничивает доступ исключительно телом самого класса. Любая попытка прочитать или записать поле снаружи (или даже из класса-наследника!) вызовет ошибку компиляции.

class A { private int x = 10; } // Использование снаружи: A a = new A(); // Console.WriteLine(a.x); // ОШИБКА!

2. База: protected и internal (Условные доступы)

Эти два модификатора служат для более точечной настройки архитектуры приложения, ограничивая доступ иерархией наследования или рамками проекта.

protected

Наследники

Члены класса с модификатором protected доступны только внутри самого класса и в любых дочерних классах (наследниках). Внешние классы через объект обращаться к ним не могут.

class A { protected int x = 10; } class B : A { void Test() { Console.WriteLine(x); // Работает в наследнике! } }

internal

Внутри сборки

Модификатор internal ограничивает область видимости одним проектом (сборкой, .exe или .dll). В рамках сборки ведет себя как public, но из другого проекта импортировать класс или поле нельзя.

internal class A { public int x = 10; } // Видно только внутри текущей сборки

Пример 1: public — доступ везде

Пример 3: protected — доступ в наследнике
C# Code class A { protected int x = 10; } class B : A { void Test() { Console.WriteLine(x); } }
Ответ: Код полностью корректен

Почему: Поле protected видно в дочерних классах (наследниках). Класс B наследуется от A, поэтому имеет законный доступ к полю x.

C# Code class A { protected int x = 10; } A a = new A(); Console.WriteLine(a.x);
Ответ: Ошибка компиляции!

Почему: Хотя protected-поля видны дочерним классам, снаружи иерархии (во внешних классах) через объект обращаться к ним нельзя. Это нарушает правила инкапсуляции.

C# Code internal class A { public int x = 10; } A a = new A(); Console.WriteLine(a.x);
Ответ: 10 (В рамках одного проекта)

Почему: Модификатор internal делает класс доступным в любом месте текущей сборки (проекта). Обращение из того же проекта полностью корректно.
Пример 6: private нельзя в наследнике
C# Code class A { private int x = 10; } class B : A { void Test() { Console.WriteLine(x); } }
Ответ: Ошибка компиляции!

Почему: Наследники НЕ получают доступ к private полям родительского класса. Поле x надежно изолировано внутри самого класса A.
Пример 7: protected в наследнике через открытый метод
C# Code class A { protected int x = 10; } class B : A { public void Show() { Console.WriteLine(x); } }
Ответ: Код полностью корректен

Почему: Обращение к protected-полю x происходит внутри дочернего класса B, что легитимно. Метод Show() имеет модификатор public, что позволяет внешним вызовам вызывать его и тем самым безопасно читать закрытые данные.
Пример 8: public доступ из любого метода
C# Code class A { public int x = 42; } void Test() { A a = new A(); Console.WriteLine(a.x); }
Ответ: 42

Почему: Открытый член класса `public int x` виден и доступен из любого внешнего метода без каких-либо ограничений.
Пример 9: internal класс в другой сборке
C# Code // В Проекте 1: internal class A { public int x = 5; } // В Проекте 2: A a = new A(); // Попытка использования
Ответ: Ошибка компиляции!

Почему: Класс A помечен как internal. Он физически не виден за пределами Проекта 1. Другие проекты (сборки) не смогут даже скомпилировать ссылку на этот тип.
Пример 10: protected-ловушка (через объект в наследнике)
C# Code class A { protected int x = 7; } class B : A { void Test() { A a = new A(); Console.WriteLine(a.x); // Ловушка! } }
Ответ: Ошибка компиляции!

Почему: Это одна из самых хитрых ловушек C#! Внутри дочернего класса B мы имеем право обращаться к protected-членам своего родителя A, но только через ссылки на тип B (или типы, унаследованные от B). 1. Ключевые слова new и this

Смысл: ссылается на текущий физический экземпляр класса. Чаще всего используется для разделения полей объекта и входящих параметров метода с одинаковыми именами.

2. Модификатор static (Принадлежит классу)

Модификатор static указывает, что член класса принадлежит самому типу данных, а не какому-то конкретному объекту.

Одно значение на весь класс

Общий ресурс

Все статические члены (поля, методы, свойства) вызываются строго через имя самого класса, без создания его физических объектов. В памяти существует ровно одна копия статического поля, общая для всех созданных экземпляров.

class A { public static int x = 10; } // Использование снаружи: Console.WriteLine(A.x); // Выведет 10. Объект создавать не нужно!
Ловушка 1: Вызов через экземпляр

В C# обращение к статическому члену через экземпляр (a.x) — это строго ошибка компиляции (CS0176):

A a = new A(); Console.WriteLine(a.x); // ❌ Ошибка компиляции CS0176
Ловушка 2: Static метод и не-static поля

Статический метод не имеет контекста объекта (нет ссылки this). Он не может напрямую использовать нестатические члены класса!

10 Экспресс-примеров на new / this / static / % / Main

Прочитайте листинг кода самостоятельно, ответьте на вопрос в заголовке, а затем нажмите кнопку **«Показать ответ»**, чтобы свериться с правильным решением и академическим объяснением.

Пример 1: new — Создание объекта класса
C# Code class A { public int x = 5; } A a = new A(); Console.WriteLine(a.x);
Выведет: 5

Почему: С помощью оператора new A() в управляемой куче создается новый объект класса A. В стек записывается ссылка на данный объект в переменной a. При выводе a.x мы получаем значение поля инициализированного объекта, то есть 5.
Пример 2: Ошибка при отсутствии new
C# Code class A { public int x = 5; } A a; Console.WriteLine(a.x);
Ответ: ❌ Ошибка компиляции

Почему: Переменная a объявлена, но не инициализирована (не выделена память под объект класса через new). Попытка прочитать поле a.x приведет к ошибке компиляции: «Использование локальной переменной, которой не присвоено значение (Use of unassigned local variable 'a')».
Пример 3: this — Различие поля и параметра
C# Code class A { public int x; public void Set(int x) { this.x = x; } }
Ответ: this.x обращается к полю объекта, а x — к параметру метода.

Почему: Параметр метода Set(int x) затеняет поле x класса. Использование ключевого слова this позволяет компилятору однозначно понять, что this.x — это переменная-член текущего экземпляра объекта в куче, а присваиваемое значение x — это аргумент, переданный в метод.
Пример 4: this нельзя использовать вне класса
C# Code // Код написан вне контекста методов класса (например, напрямую в файле): this.x = 10;
Ответ: ❌ Ошибка компиляции

Почему: Ключевое слово this ссылается строго на текущий экземпляр класса и имеет смысл только внутри нестатических методов, свойств или конструкторов этого класса. Вне класса или в статических методах ключевое слово this недоступно и вызывает ошибку компиляции.
Пример 5: static — Общее поле на весь класс
C# Code class A { public static int x = 10; } A a1 = new A(); A a2 = new A(); A.x = 50; Console.WriteLine(A.x);
Выведет: 50

Почему: Статическая переменная x принадлежит непосредственно классу A. Вне зависимости от количества созданных объектов (переменные a1 и a2 здесь никак не влияют на `x`), ячейка памяти в метаданных типа ровно одна. Изменение значения A.x = 50 переписывает эту общую ячейку, и вывод показывает новое значение 50.
Пример 6: static нельзя вызывать через экземпляр объекта
C# Code class A { public static int x = 10; } A a = new A(); Console.WriteLine(a.x);
Ответ: ❌ Ошибка компиляции

Почему: В C# спецификация языка строго **запрещает** обращаться к статическим членам класса через ссылки на экземпляры объектов (ошибка компиляции CS0176). Правильный и единственный рабочий синтаксис — обращение строго через имя класса: Console.WriteLine(A.x);.
Пример 7: static метод и нестатическое поле
C# Code class A { public int x = 10; public static void Test() { Console.WriteLine(x); } }
Ответ: ❌ Ошибка компиляции

Почему: Статический метод Test() принадлежит самому типу A и может вызываться без создания объектов. Нестатическое поле x принадлежит объектам и физически существует только после их создания в куче. Обращение к нестатическому полю напрямую из статического контекста запрещено (CS0120), так как компилятору неизвестно, у какого именно объекта брать значение x.
Пример 8: % — Остаток от деления
C# Code Console.WriteLine(17 % 5);
Выведет: 2

Почему: Оператор % вычисляет остаток от целочисленного деления. 17 делится на 5 как 3 нацело (15), а оставшаяся разность 17 - 15 = 2 возвращается в качестве результата.
Пример 9: Проверка четности числа через %
C# Code int x = 8; if (x % 2 == 0) { Console.WriteLine("even"); }
Выведет: even

Почему: Так как число 8 делится на 2 нацело без остатка, выражение 8 % 2 возвращает 0. Условие 0 == 0 верно (true), и программа выводит в консоль строку even.
Пример 10: Main — Точка входа в программу
C# Code class Program { static void Main() { Console.WriteLine("Hello"); } }
Выведет: Hello

Почему: Метод Main объявлен с модификатором static и возвращаемым типом void. Он является корректно оформленной точкой входа. При запуске среда CLR найдет этот метод и выполнит код внутри него, выведя строку Hello.

1. Указатели — Самая Важная Тема

Указатель — это переменная, которая в качестве своего значения хранит физический **адрес ячейки памяти**, в которой лежат другие данные.

Оператор &

Взятие адреса

Смысл: возвращает адрес переменной в памяти. «Где физически лежит переменная в оперативной памяти».

int a = 10; printf("%p", &a); // Выведет физический адрес (например, 0x7ffd580b)

Оператор *

Разыменование

Смысл: **получает доступ к значению по адресу**, на который ссылается указатель. «Пойти по адресу в памяти и прочитать/записать значение».

int a = 10; int *p = &a; // p хранит адрес переменной a printf("%d", *p); // Выведет значение a, то есть 10
ЛОВУШКА ГОСА: Изменение оригинальной переменной и дикие указатели

1. Если выполнить *p = 20; (при p = &a), то **значение самой переменной a изменится на 20**, так как мы переписали ячейку памяти напрямую.
2. Дикий указатель: int *p; *p = 5; → **ужасная ошибка!** Указатель p не инициализирован (ссылается на случайный мусорный адрес). Запись значения в случайный адрес вызовет немедленный краш программы (Segmentation Fault) или порчу памяти.

2. Управление памятью: malloc и free

В языке C динамическое выделение памяти в куче (heap) происходит вручную с помощью системных функций из библиотеки stdlib.h.

malloc

Выделение

Смысл: выделяет блок памяти в куче указанного размера. Возвращает нетипизированный указатель void*, который приводится к нужному типу.

// Выделяем память под один int (4 байта): int *p = (int*)malloc(sizeof(int)); *p = 9;

free

Освобождение

Смысл: освобождает ранее выделенный блок динамической памяти. Предотвращает утечки памяти (Memory Leaks).

// Освобождаем память: free(p);
ДВЕ КРИТИЧЕСКИЕ ОШИБКИ КУЧИ

1. Double Free (Двойное освобождение): попытка сделать free(p); free(p); для одного и того же адреса. Это разрушает менеджер кучи и вызывает аварийное завершение программы.
2. Use-After-Free (Использование после освобождения): обращение к значению *p после вызова free(p);. В ячейке уже лежит системный мусор, чтение приведет к непредвиденному поведению (UB).

3. Массивы и адресная арифметика

В языке C имя массива неявно преобразуется в указатель на его первый физический элемент.

СВЯЗЬ: Имя массива = Адрес первого элемента

Адресная арифметика

Выражение arr эквивалентно &arr[0]. А разыменование имени массива *arr дает значение первого элемента arr[0].

4. Логические vs Битовые операторы

Комиссия обожает ловить студентов на невнимательности при чтении условий. Знайте разницу между логикой и битовой маской!

Логические (&& и ||)

Истина / Ложь

Смысл: оценивают логическое И / ИЛИ. Возвращают строго 1 (true) или 0 (false).

C# Code struct P { public int x; } P a = new P(); a.x = 5; P b = a; b.x = 10; Console.WriteLine(a.x);

Почему: В C# структуры являются value type (значимыми типами). При присваивании P b = a создается полная копия структуры в стеке. Изменение поля b.x никак не влияет на a.x.
Задача 2: class копирование по ссылке
C# Code class P { public int x; } P a = new P(); a.x = 5; P b = a; b.x = 10; Console.WriteLine(a.x);
Ответ: 10

Почему: Классы в C# — это reference type (ссылочные типы). Переменная b указывает на тот же физический объект в куче, что и a. Изменение b.x = 10 меняет поле общего объекта, поэтому вывод a.x равен 10.
Задача 3: Передача параметра через ref
C# Code void F(ref int x) { x += 2; } int a = 3; F(ref a); Console.WriteLine(a);
Ответ: 5

Почему: Модификатор ref заставляет компилятор передавать аргумент по ссылке. Внутри метода F мы работаем напрямую со стековой ячейкой переменной a, увеличивая её на 2.
Задача 4: Использование out параметров
C# Code void F(out int x) { x = 7; } int a; F(out a); Console.WriteLine(a);
Ответ: 7

Почему: Параметр out аналогичен ref, но обязывает метод обязательно выполнить присваивание до выхода из него. Исходная переменная a может быть не инициализирована до вызова метода, что здесь и происходит. Результат — 7.
Задача 5: Неинициализированный параметр в ref
C# Code void F(ref int x) { x++; } int a; F(ref a); // ❌ Где-то здесь подвох?
Ответ: ❌ Ошибка компиляции

Why: В отличие от out, модификатор ref строго **требует**, чтобы переменная, передаваемая по ссылке, была гарантированно инициализирована до момента вызова метода. Переменная int a; пуста, поэтому компилятор выдаст ошибку CS0165.
Задача 6: Виртуальные методы (virtual / override)
C# Code class A { public virtual void F() => Console.WriteLine("A"); } class B : A { public override void F() => Console.WriteLine("B"); } A obj = new B(); obj.F();
Ответ: B

Почему: Здесь срабатывает позднее связывание (полиморфизм). Объект создан как B, а переменная приведена к базовому классу A. Так как метод F объявлен как virtual и переопределен через override, рантайм вызывает версию метода фактически созданного объекта, то есть класса B.
Задача 7: Абстрактные методы
C# Code abstract class A { public abstract void F(); } class B : A { public override void F() => Console.WriteLine("B"); } A obj = new B(); obj.F();
Ответ: B

Почему: Абстрактный метод базового класса не имеет реализации и обязан быть переопределен в дочернем классе. Механизм вызова аналогичен виртуальным методам: во время выполнения вызывается переопределенный метод дочернего объекта.
Задача 8: Вызов методов интерфейса
C# Code interface I { void F(); } class A : I { public void F() => Console.WriteLine("X"); } I obj = new A(); obj.F();
Ответ: X

Почему: Переменная типа интерфейса I ссылается на экземпляр класса A, реализующего данный интерфейс. Вызов obj.F() успешно разрешается в метод класса A.
Задача 9: Разрешение коллизии имен через `this`
C# Code class A { public int x; public void F(int x) { this.x = x; } } A a = new A(); a.F(5); Console.WriteLine(a.x);
Ответ: 5

Почему: Ключевое слово this указывает на текущий экземпляр. В строке this.x = x; компилятор понимает, что левый x — это поле класса, а правый — локальный аргумент метода. В результате поле успешно принимает значение 5.
Задача 10: Обращение к нестатическому члену из static
C# Code class A { public int x = 5; public static void F() { Console.WriteLine(x); } }
Ответ: ❌ Ошибка компиляции

Почему: Статический метод F() не привязан к конкретному объекту в куче (для него нет ссылки this). Попытка напрямую прочитать нестатическое поле x вызовет ошибку компиляции CS0120: «Для нестатического поля, метода или свойства требуется ссылка на объект».
Задача 11: Оператор остатка от деления в C
C Code printf("%d", 17 % 5);
Ответ: 2

Почему: Классический оператор остатка. 17 делится на 5 как 3 нацело, а остаток равен 17 - (5 * 3) = 2.
Задача 12: Побитовое умножение в Си (Logical & vs &&)
C Code int a = 0; if (a & 1) printf("X");
Ответ: нет вывода

Почему: В условии используется побитовое И (&). Двоичное представление 0 & 1 дает 0 (false в C). Условие ложно, поэтому в консоль ничего не выводится.
Задача 13: Побитовое сложение в Си (Logical | vs ||)
C Code int a = 1; if (a | 0) printf("X");
Ответ: X

Почему: Выполняется побитовое ИЛИ (|). Выражение 1 | 0 возвращает 1. В языке C любое ненулевое число оценивается как Истина (true). Условие истинно, и выводится символ X.
Задача 14: Изменение значения переменной через указатель
C Code int a = 10; int *p = &a; *p = 20; printf("%d", a);
Ответ: 20

Почему: Переменная p хранит физический адрес переменной a. Выполняя разыменование и запись *p = 20;, мы перезаписываем значение в оригинальной ячейке переменной a.
Задача 15: Запись по дикому (неинициализированному) указателю
C Code int *p; *p = 5;
Ответ: ❌ Ошибка выполнения / Неопределенное поведение (Segmentation Fault)

Почему: Указатель p объявлен, но не инициализирован никаким адресом (он "дикий" и ссылается на случайную память). Попытка разыменовать его и записать туда число 5 — критическая ошибка операционной системы, ведущая к аварийной остановке программы.
Задача 16: Разыменование имени массива в C
C Code int a[] = {1,2,3}; printf("%d", *a);
Ответ: 1

Почему: Имя массива в C неявно приводится к указателю на его первый элемент. То есть a — это то же самое, что &a[0]. Соответственно, разыменование *a возвращает первый элемент, то есть 1.
Задача 17: Выделение памяти через malloc
C Code int *p = malloc(sizeof(int)); *p = 9; printf("%d", *p);
Ответ: 9

Почему: Функция malloc выделяет свободную ячейку в динамической куче (heap) размером в 4 байта (размер int). Мы успешно записываем по этому адресу число 9 и выводим его.
Задача 18: Чтение памяти после free (Use-After-Free)
C Code int *p = malloc(sizeof(int)); free(p); printf("%d", *p);
Ответ: ❌ Неопределенное поведение (Undefined Behavior / UB)

Почему: Память по указателю p уже была официально возвращена операционной системе вызовом free(p). Попытка прочитать данные из освобожденного адреса — грубое нарушение правил работы с памятью. Программа может вывести мусор, старое значение или аварийно упасть.
Задача 19: Двойное освобождение указателя (Double Free)
C Code int *p = malloc(sizeof(int)); free(p); free(p);
Ответ: ❌ Ошибка кучи / Аварийное завершение (Double Free)

Почему: Повторный вызов free() для одного и того же адреса памяти приводит к разрушению внутренних дескрипторов менеджера памяти кучи. Современные ОС моментально прерывают выполнение такой программы из соображений безопасности.
Задача 20: Целочисленное деление в C
C Code printf("%d", 5 / 2);
Ответ: 2

Почему: Поскольку оба операнда деления — целые числа (int), C выполняет деление нацело. Вся дробная часть просто отбрасывается, результатом выражения является строго 2.
Задача 21: Явное приведение float к int
C Code int a = (int)5.9; printf("%d", a);
Ответ: 5

Почему: Приведение вещественного типа к целочисленному всегда отсекает дробную часть, не выполняя математического округления. Поэтому значение 5.9 превращается в ровно 5.
Задача 22: Условие бинарного поиска

👉👉 Вопрос: можно ли применить бинарный поиск к несортированному массиву?

Ответ: Нет

Почему: Алгоритм двоичного (бинарного) поиска опирается на принцип упорядоченности данных: отсечение половины диапазона на каждом шаге корректно работает только в том случае, если все элементы строго отсортированы. На несортированном массиве бинарный поиск выдаст неверный результат.
Задача 23: Передача структуры по значению в метод
C# Code struct P { public int x; } void F(P p) { p.x = 10; } P a = new P(); a.x = 5; F(a); Console.WriteLine(a.x);
Ответ: 5

Почему: Структура — это значимый тип. Передавая её в метод F(P p) без модификаторов ref/out, мы неявно создаем полную копию структуры в стеке метода. Любые манипуляции над p.x происходят с локальной копией и исчезают при возврате в Main.
Задача 24: Передача класса в метод по ссылке
C# Code class P { public int x; } void F(P p) { p.x = 10; } P a = new P(); a.x = 5; F(a); Console.WriteLine(a.x);
Ответ: 10

Почему: Класс — ссылочный тип. Передавая a в метод, мы копируем адрес ссылки на объект в куче. Внутри метода F переменная p указывает на ту же физическую ячейку в памяти кучи, переписывая поле x на 10.
Задача 25: Присвоение null классу
C# Code class A { } A a = null; Console.WriteLine(a == null);
Ответ: True

Почему: Любая переменная ссылочного типа (класса) может принимать значение null, обозначающее отсутствие ссылки на реальный объект в управляемой куче. Сравнение a == null истинно.
Задача 26: Попытка занулить (null) структуру
C# Code struct P { public int x; } P p = null; // ❌ Так ли это законно?
Ответ: ❌ Ошибка компиляции

Почему: Переменные значимых типов (структур, примитивных чисел) хранят свои данные непосредственно в стеке и не могут содержать значение null. Попытка напрямую присвоить null структуре вызовет ошибку компиляции CS0037: «Не удается преобразовать значение null в тип 'P', так как он не является ссылочным типом».
Задача 27: Наследование структур друг от друга
C# Code struct A { } struct B : A { } // ❌ Наследование?
Ответ: ❌ Ошибка компиляции

Почему: В C# структуры полностью исключены из иерархии ООП-наследования пользовательских типов. Структура не может наследоваться от другой структуры или класса (все структуры неявно помечены компилятором как sealed).
Задача 28: Выполнение finally при return
C# Code try { return; } finally { Console.WriteLine("F"); }
Ответ: F

Почему: Конструкция finally гарантирует свое выполнение при любом сценарии выхода из блока try — включая прямой вызов оператора возврата из метода return. Символ F будет успешно выведен на экран перед выходом.
Задача 29: Недостижимый код после throw
C# Code throw new Exception(); Console.WriteLine("X");
Ответ: ❌ Ошибка компиляции (или предупреждение, блокирующее сборку)

Почему: Компилятор C# проводит статический анализ путей выполнения. Оператор throw безусловно прерывает ход выполнения метода. Любой код, расположенный непосредственно после него на той же ветке, физически недостижим, что вызывает ошибку компиляции CS0162: «Обнаружен недостижимый код (Unreachable code detected)».
Задача 30: Класс как ссылка в методе (Мастер-Класс)
C# Code class A { public int x; } void F(A a) { a.x = 5; } A a = new A(); a.x = 1; F(a); Console.WriteLine(a.x);
Ответ: 5

Почему: Это эталонная задача на понимание передачи ссылочных аргументов. Метод F принимает ссылку на созданный объект a. Перезапись поля a.x = 5 внутри метода физически изменяет поле оригинального объекта в управляемой куче. На выходе из метода a.x равен 5.

1. Жизненный цикл программного обеспечения (SDLC)

Жизненный цикл ПО (SDLC - Software Development Life Cycle) — это весь период создания и использования программного обеспечения, состоящий из фиксированных этапов, идущих в строгом логическом порядке: от первоначальной идеи до полной поддержки или вывода из эксплуатации.

📌 Основные этапы (ОЧЕНЬ ВАЖНО ЗНАТЬ ПО ПОРЯДКУ!)

1

Анализ требований

Сбор информации, общение с заказчиком, составление ТЗ. С этого ВСЕГДА начинается ЖЦ ПО.

2

Проектирование

Создание архитектуры системы, проектирование баз данных, выбор стека и библиотек.

3

Реализация (Кодирование)

👉 Идет сразу после проектирования! Непосредственное написание программного кода разработчиками.

4

Тестирование

👉 Здесь выявляют и исправляют ошибки! Проверка программы на соответствие исходным требованиям.

5

Внедрение

Передача программы пользователям, развертывание на серверах (деплой), настройка окружения.

6

Сопровождение

Поддержка программы после релиза, исправление багов, выпуск обновлений. Этим ЖЦ ПО завершается.

2. Модели жизненного цикла ПО

Модель жизненного цикла определяет стратегию разработки ПО и взаимосвязь между этапами. На госе нужно знать две основные, классические модели:

Каскадная модель (Waterfall)

Линейная / Строгая

Суть: Все этапы идут строго друг за другом. Переход к следующему этапу возможен ТОЛЬКО после полного завершения предыдущего. Шаги назад не предусмотрены.

Требования → Проект → Код → Тест → Релиз
Плюсы:
  • Простая и понятная структура
  • Прозрачное планирование и фикс цены
Минусы:
  • Нельзя легко вернуться на шаг назад
  • Ошибки в требованиях выявляются слишком поздно (на этапе теста)
Экзамен-ключ: Каскадная модель всегда строго последовательная, однопроходная и негибкая.

Спиральная модель (Spiral)

Итеративная / Риски

Суть: Процесс разработки идет витками (итерациями). Каждый виток спирали включает: планирование, анализ рисков, разработку прототипа и оценку результатов заказчиком.

Планирование → Риск-анализ → Прототип → Тест
Плюсы:
  • Исключительная гибкость и учет изменений
  • Фокус на минимизацию рисков
Минусы:
  • Сложность управления проектом
  • Высокая стоимость из-за постоянного риск-анализа
Экзамен-ключ: Спиральная модель ВСЕГДА связана с риск-анализом, прототипированием и итерациями!

3. Модульность и её свойства

Модульность — это принцип разделения программы на отдельные независимые части (модули), каждая из которых выполняет свою локальную задачу. Модулем может быть отдельная функция, класс, библиотека или файл.

Свойства модуля (Любят на госе!)

1. Независимость (Изоляция)

Модуль работает отдельно и скрывает детали своей реализации. Изменения внутри модуля не ломают остальную систему.

2. Повторное использование (Reusability)

Один и тот же модуль можно использовать в разных частях программы или даже переносить в другие проекты без изменений.

3. Заменяемость (Взаимозаменяемость)

Модуль можно легко вырезать и заменить другим с таким же интерфейсом, не переписывая все приложение целиком.

Что запомнить?

Главное свойство хорошего модуля — это его **независимость**. В программировании стремятся к слабому зацеплению (Low Coupling) между модулями и сильной связности (High Cohesion) внутри одного модуля.

Вопрос с госа: «Какое свойство модуля является ключевым?»
👉 Ответ: Независимость!

4. Тестирование ПО (White-box vs Black-box)

Тестирование — проверка программы на соответствие требованиям. По уровню доступа к исходному коду методы тестирования делятся на два противоположных подхода:

Структурное тестирование (White-box)

«Белый ящик» / Код

Тестировщик имеет **полный доступ к исходному коду** программы. Тесты строятся на внутренней структуре логики.

Что проверяется:
  • Все ветки условных операторов (if-else)
  • Все циклы при различных условиях
  • Пути выполнения функций
Экзамен-ключ: Если видишь фразу «основано на коде» или «анализ путей выполнения» — это 100% структурное (white-box) тестирование.

Функциональное тестирование (Black-box)

«Черный ящик» / Требования

Тестировщик **НЕ видит код**. Программа рассматривается как черный ящик. Проверка идет исключительно снаружи: подаем входные данные $\rightarrow$ сравниваем результат.

Что проверяется:
  • Соответствие программы спецификации и требованиям
  • Корректность ввода-вывода (вход → выход)
  • Удобство интерфейса пользователя (UI/UX)
Экзамен-ключ: Если видишь фразу «без знания кода» или «проверка требований» — это 100% функциональное (black-box) тестирование.

Словарь госа: Базовые термины

  • Алгоритм — точная последовательность действий (шагов) для решения задачи.
  • Программа — реализация алгоритма на конкретном языке программирования.
  • Данные — информация (переменные, файлы, структуры), с которой работает программа.
  • ПО (Software) — совокупность программ, данных и сопутствующей документации.

Что запомнить на 100%?

ЖЦ ПО: Анализ → Проект → Код → Тест → Внедрение → Сопровождение.

Модели: Каскадная (строгие шаги), Спиральная (круги, итерации + риски).

Модули: Независимость, переиспользование, заменяемость.

Тест: Структурное (код, white-box), Функциональное (требования, black-box).

Суть каскадной модели

Понимаю, что каскадная модель — это строгая последовательность, где нельзя перепрыгивать назад, а ошибки находят поздно.

Суть спиральной модели

Знаю, что спиральная модель — это итеративный подход, ориентированный на анализ рисков и создание прототипов на каждом витке.

Свойства модуля

Помню 3 важнейших свойства модуля: независимость (главное!), переиспользование и заменяемость.

Виды тестирования по доступу к коду

Могу дать четкие определения: структурное (White-box, по исходному коду) и функциональное (Black-box, без кода, по требованиям).

Соотношение Модуль / Класс / Функция

Понимаю, что библиотека/файл — это модуль, класс — шаблон объекта, функция — отдельная операция.

Базовая терминология ГИА

Знаю наизусть разницу между Алгоритмом (описание шагов) и Программой (реализация шагов на языке).

Сопровождение ПО

Помню, что это этап поддержки, исправления дефектов и адаптации системы после сдачи в промышленную эксплуатацию.

Вопрос 1: Жизненный цикл ПО начинается с:
Верно! Любой жизненный цикл ПО (SDLC) всегда начинается с этапа анализа требований, на котором определяются цели системы, ее функции и составляется ТЗ.
Вопрос 2: Что идет после проектирования?
Верно! После этапа проектирования архитектуры системы следует этап реализации (кодирования), где программисты непосредственно пишут код на основе проектных решений.
Вопрос 3: На каком этапе ищут ошибки в программе?
Верно! Этап тестирования специально предназначен для выявления дефектов, расхождений с требованиями и багов в написанном коде с целью их последующего исправления.
Вопрос 4: Каскадная модель характеризуется:
Верно! Каскадная модель (Waterfall) предполагает строго последовательное (линейное) прохождение этапов: каждый новый этап начинается только тогда, когда завершен предыдущий, без возвратов назад.
Вопрос 5: Спиральная модель основана на:
Верно! Спиральная модель делает упор на постоянный анализ проектных рисков на каждом витке (итерации) спирали, постепенно улучшая продукт через создание прототипов.
Вопрос 6: Какая модель более гибкая?
Верно! Спиральная модель намного гибче каскадной, поскольку позволяет вносить изменения в требования и спецификации на каждом новом витке разработки.
Вопрос 7: Модуль — это:
Верно! Модуль — это логически обособленная и функционально завершенная часть системы (класс, файл с функциями, внешняя библиотека), решающая определенную локальную задачу.
Вопрос 8: Главное свойство модуля:
Верно! Независимость (слабая зацепленность с остальными модулями) является фундаментальным свойством модуля, позволяющим разрабатывать, тестировать и изменять его изолированно от всей остальной системы.
Вопрос 9: Модуль можно:
Верно! За счет изоляции и четких интерфейсов взаимодействия модули обладают важным качеством переиспользования (повторного применения) в других проектах или частях программы.
Вопрос 10: Структурное тестирование основано на:
Верно! Структурное тестирование (метод «белого ящика») целиком основывается на анализе внутренней структуры исходного кода — ветвлений, условий, вызовов функций.
Вопрос 11: Функциональное тестирование основано на:
Верно! Функциональное тестирование (метод «черного ящика») строится на исходных внешних требованиях к ПО и проверяет соответствие реального поведения системы задекларированному.
Вопрос 12: White-box тестирование — это:
Верно! Термин White-box («белый ящик» или «прозрачный ящик») означает, что тестирование осуществляется со знанием внутренней логики и исходного кода приложения.
Вопрос 13: Black-box тестирование — это:
Верно! Термин Black-box («черный ящик») символизирует, что внутреннее устройство системы скрыто от тестировщика. Проверка идет исключительно на уровне интерфейсов ввода-вывода данных.
Вопрос 14: Алгоритм — это:
Верно! Алгоритм — это абстрактная, точная, понятная исполнителю последовательность элементарных шагов или действий, приводящих к решению поставленной задачи.
Вопрос 15: Программа — это:
Верно! Компьютерная программа представляет собой конкретную физическую реализацию определенного алгоритма, записанную на понятном компьютеру языке программирования.
Вопрос 16: Жизненный цикл заканчивается:
Верно! Жизненный цикл ПО длится вплоть до прекращения поддержки системы. Таким образом, завершающим этапом является сопровождение ПО (поддержка, багфиксы).
Вопрос 17: Спиральная модель включает:
Верно! Уникальной отличительной чертой спиральной модели является обязательный, глубокий этап анализа рисков на каждом новом витке разработки прототипа.
Вопрос 18: Каскадная модель:
Верно! Каскадная модель является классической линейной моделью — движение идет в одну сторону строго последовательно от первого этапа к последнему.
Вопрос 19: Какой этап идет первым?
Верно! Разработка программного обеспечения всегда стартует со сбора, обобщения и глубокого анализа требований, чтобы понимать контуры будущей системы.
Вопрос 20: Что такое сопровождение ПО?
Верно! Сопровождение ПО (Maintenance) — это деятельность по технической поддержке программной системы после ее ввода в эксплуатацию, исправлению скрытых багов, оптимизации и добавлению небольших фич.
